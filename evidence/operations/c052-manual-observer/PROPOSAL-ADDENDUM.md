## 結論と追加事実

**Bは条件付きで現契約と同じ観測義務を満たせる。IAB操作ツールの接続復旧をBの前提にはしない。** 本人が通常のIABで凍結済み入力を送り、実際の成果物リンクを開く。開発は、その操作記録と同じ実行のホスト状態・HTTP本文・receiptを照合する。入力担当の変更だけでは新scopeや本人承認gateにならない。ただし以下の対応関係が取れない実測をPASSにはしない。

本人のHR005回答と添付画像を確認した。PAL開発内に公開OpenAI説明ページが表示されている。開発側の報告では、その後の正式inventory一回でもIABは列挙されなかった。A0は「本人による公開ページ表示DONE／tool接続NOT_ESTABLISHED」。公開ページ表示はPALのoriginや将来artifactの許可・表示成功を証明しない。元C045の本文拒否とは別の事実で、get/create/native/CDPの追加retryは不要。

前回提案の「tool接続後にA」は自動観測案の条件として履歴に残す。Bの準備まで同じ条件で止める必要はない。準備済み静的fixtureの本人操作は、必要なら通常リンクの開き方と観測の受渡しを確かめる無モデルの予行として使えるが、製品の合格条件や全URLの許可証明にはしない。今回はその操作も依頼・実行しない。

## 同等性を確認する最小の対応表

元contractのobservation_contractは「実UI」「表示リンクから実artifactを開く」「HTTP bytes/size/SHA256とreceiptの照合」を要求する。単一observerやブラウザー内部のネットワーク証明は要求していない。以下は新しい合格条件ではなく、既存義務の担当と証拠を明示したもの。

| 元の義務 | 本人の通常操作・画面の証拠 | 開発側の照合 |
|---|---|---|
| 実際の通常会話UIから全測定入力を送る | 同一hostの通常会話欄へ、用意済みの原文を一度送る。実際の返信とSession receiptを保持 | UI receiptのkey/record_idをprimary_turns.client_key/record_id、実記録本文、実Primary結果へ結ぶ。文字列と入力順は原契約どおり |
| 質問・対象選択を経た所定の後続入力 | 実際の返信を見て、該当条件を満たすときだけ所定の次文を通常会話欄から送る | 前後のGoal/Attempt/question/revision/epoch/source/criteriaを確認。所定外の回答・救済入力はしない |
| 実成果物を表示リンクから開く | 完了した会話カードのリンクを実際に押し、開いたIABページを記録。手入力したartifact URLや要約で代用しない | 元会話のsource_event_id→goal.completedのartifact_id、表示後の正確なorigin/pathのartifact_id、receipt.artifact_idが一致すること |
| 同じ実出力のHTTP本文とreceipt | 表示されたページのURLと本文が分かる画面、クリックした経緯の操作記録 | 同一の稼働host・同一artifact URLを通常HTTP GETで読み、成功・非redirect・Content-Typeと全bytesの長さ/SHA256を照合。receipt→Attempt→Goal/revision/epoch/manifestが一致 |
| first outcome・上限・終了・採点 | 次の指示を勝手に追加せず、エラーや拒否もそのまま提示 | 独立cap、fresh proof、600秒、実呼出し数、最初の結果、固定oracle、プロセス終了とport閉鎖を管理。採点・保存は開発が行う |

既存の会話画面、Session receipt、/api/state、/api/operation、/api/artifactを使う範囲で案を成立させられる。新UI、新DB schema、入力のHTTP直送、ブラウザー内script、DOM/CDP計測を前提にしない。Session receiptはブラウザー内の表示であり、単独でホスト証拠にはしない。accepted_atもクライアント時刻なので、イベント順序・制限時間はホスト観測と結び付ける。

画面とHTTPの全bytesが暗号的に同一であることまで画面写真で証明できる、とは主張しない。元契約と同じく、実リンクの遷移記録、正確なartifact ID、表示本文、同じ稼働hostの不変artifactとreceiptを組み合わせる。一般的な「開けた」という返事だけや、URL/IDの読めない画面だけでは足りない。住所欄に全pathが省略される場合は、通常のUI操作で確認した正確なURLも保持する。これは未拒否の新規出力だけに限定する。

## 実施する場合の一件の流れ

1. **モデルを呼ぶ前に準備する。** 開発がこの技術的手順と証拠項目を記録し、現行のclean pushed HEAD、product/UI/元contractのhash、対象case、原文、分岐条件、実行順、cap、既存の有限終了手順を固定する。本人には短い通常操作だけを提示できる状態にしておく。公開docs表示済みを、これから600秒以内の操作へ参加できるという返事には読み替えない。
2. **一つの未実行hostだけを開始する。** 既存の独立DB、public Storeによる所定setup、production entrypoint、fresh既存認証/追加課金なしの一回proof、元のcapを使う。新しいoriginへの通常アクセスに適用される拒否がないことを確認し、本人が実UIを開けてから測定入力へ進む。確認待ちで先に複数hostやproviderを起動しない。proof/host期限を待ち時間のために延長・更新しない。
3. **入力と条件を守る。** 本人は指定原文を通常会話欄へ一回送る。開発はreceiptとcanonical結果を照合する。後続入力の許否は既存oracleで判断し、本人に採点や内部状態の判断を任せない。余分な入力、言い換え、二重送信、想定外の質問があれば、最初の結果と消費を保持して止める。手順逸脱を都合よくVOIDや成功へ付け替えない。
4. **実リンクの表示を先に確認する。** 本人が実際の生成artifactのリンクを押した記録、元会話と表示先の画面・正確なURLを取得する。新caseであっても拒否画面・アクセス制限・新権限要求が現れたらそこで止める。開発はその本文をHTTP/DB/ファイル/本人中継で取得しない。表示観測と許可が未確認のまま、照合名目で本文を先取りしない。
5. **開発が同一出力を照合して終了する。** 許可された同一URLだけで全本文を取得し、上表の対応と固定semantic oracleを判定する。直接SQLでの状態修正や旧DB参照はしない。稼働中の観測を600秒以内で閉じ、owned host終了・port閉鎖を確認してから保存と詳細評価を仕上げる。遅れて届いた画面だけで期限内の表示を断定しない。期限切れは保留・未検証の証拠として残し、再生成しない。

後続hostは各一回の独立first sampleとして既存順で扱い、最初の失敗・制限で停止する。ブラウザー拒否後に別port/別browser/別手段を試して続きを通す流れにはしない。
