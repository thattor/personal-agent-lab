# 再検討：72h soakとPersonal Useの受け入れ順序（Opus見解）

ご指示どおりテキストのみで回答します。plan fileは作成せず、ツールも使いません。以下は**推奨**です。ユーザーが採用するまで、受け入れ定義は何も変わりません。

## 0. 前回のOpus回答の位置づけ

前回私は「scripted trafficを実人間ターンとして数えるのは過大主張」として退けました。これは「既存ゲートを下げるな」という指示の範囲で、**忠実に解釈した結果**です。72hという基準が個人利用に最適だと独立に検証したわけではありません。今回は独立に評価します。

現状の扱いは次のとおりです。
- soak03（10ターン、2セッション、1時間未満）は**S0-13未達**のままです。
- Stable-0は**未達**です。
- 既存の証跡を遡って付け替えることはしません。

## 1. ユーザーの異議への結論

**ユーザーの異議は正当です。** 個人利用の優先順位は「期待どおり動くこと」が「長期観測」より先です。

さらに重要な点として、**現状のまま72hを回しても「期待どおり」を何も証明しません。** サーバーの会話経路は常にMockProviderで、返答は固定のacknowledgementと依頼のecho（オウム返し）です。live smokeも`quality_claim:none`で、UTF-8として空でないこととhashしか確認していません。このため72h mock soakの価値は小さく、それを完了条件の律速にするのは順序が逆です。

## 2. Astraへの応答と反論

**Q1（72hで何の故障を見ているのか）**
- 72という数字に独立したリスク根拠はない、という点はAstraに同意します。
- ただし、実時間でしか出ない故障は実在します。
  - macOSのsleep/wakeや蓋閉じ
  - 実時計のジャンプ
  - lease、TTL、outbox backoffの実時間挙動
  - SQLite WALの肥大とcheckpoint
  - ログの肥大
  - **Claude Pro公式認証の期限切れと更新**
- これらはSIGKILLテストでは見えません。
- **反論点：** このうち最も現実的な認証失効は、mock経路では原理的に観測できません。つまり72hを回すなら実provider経路で回すべきで、mockの72hはほぼ無意味です。
- 残りの大半はfake clockと、SIGSTOP/SIGCONTによる時計ジャンプの決定的テストで、安く代替できます。

**Q2（mock UIと非意味的smokeで「覚える・返す・何が起きたか」を満たすか）**
- 満たしません。これが最大の機能ギャップだという点でAstraに同意します。

**Q3（時間観測の前に要求-成果物マトリクスを置くべきか）**
- 置くべきです。ただし小さく保ちます（10〜15行）。
- 各行は「ユーザーの期待 → コード経路 → 決定的テスト → 人間判定シナリオ」を対応させます。

**Q4（保護を維持したまま72hを非ブロッキング観測にできるか）**
- 可能です。条件は二つです。
  - 安全不変条件（破損、重複、stale apply、forget、秘密情報）は**常時ブロッキング**のまま残します。
  - 「時間と回数の到達」だけを非ブロッキングにします。
- 完了定義の変更には、ユーザーの明示的な採用が必要です。

**Q5（リセット方針）**
- 影響範囲ベースでの無効化に賛成です。ただし**fail-closed**にします。
  - 各証跡行に依存コンポーネントのhashを記録します。
  - 影響範囲の分類が不確実なら全リセットします。
- 「表示専用の翻訳」でも、次に該当するものは表示専用ではありません。
  - 保存されるデータに入るもの
  - providerに送るpromptに入るもの
  - ログやinspectの出力に入るもの

## 3. 定義を変えることで起きる回帰リスク

1. sleep/wakeや認証失効など、実時間でしか出ない故障の検出が後回しになります。
2. 「Stable-0」という名前の意味が変わり、過去の議論や証跡と齟齬が出ます。
   - 対策：Stable-0を書き換えず、**新ラベル（例：Personal-Usable-1）**を別に定義します。
3. 実provider接続という大きな変更が安全上クリティカルな経路に入り、既存のPASS（S0-01..12）の前提を壊す可能性があります。
4. LLMの返答品質は決定的に判定できないため、「完全に期待どおり」が際限なく膨らむおそれがあります（goal creep）。

## 4. 最小で安全な代替シーケンス（推奨）

**P0 ユーザー承認（コード変更なし）**
- Stable-0は凍結し、未達のまま保持します。
- 新しい完了ラベルPersonal-Usable-1と、その定義を採用するかどうかを決めます。
- 72hを非ブロッキング観測に格下げすることを承認するかどうかを決めます。

**P1 要求マトリクス（文書のみ。内容はユーザー承認、整合性はSWEレビュー）**
- 「覚える」「返す」「何が起きたか説明する」などを具体的なシナリオにします。
- 各シナリオの合否はユーザーが判定する形で記述します。

**P2 実装（実装とSWEレビューが必要）**
- 既存の公式・追加料金なしのClaude Pro smoke経路を、会話laneに接続します。
  - 新しい認証、有料API、公開範囲の拡大は導入しません。
  - Executorはtool-freeかつimmutableのまま維持します。
  - fence、outbox、冪等性の仕組みをそのまま通します。
  - MockProviderはテスト専用に残します。
- 「覚える」を実現するため、canonical SQLiteから文脈を組み立てる経路を明確にします。
- 「何が起きたか」の説明は、可能な限りログから決定的に生成します。
- 時間依存の決定的テストを追加します。
  - fake clock
  - 時計ジャンプ
  - 認証失効と更新の模擬

**P3 回帰と機能受け入れ**
- S0-01..12を変更後のコードで再実行します（影響範囲ルールに従う）。
- ユーザーが実UIでP1のシナリオを人間として実行し、合否を判定します。

**P4 Personal-Usable-1の宣言（ユーザーのみが行う）**

**P5 非ブロッキング継続観測（実providerで実利用）**
- 少なくとも次の事象を1回ずつ含めます：sleep/wake、再起動、認証更新。
- 起動時（または日次）に自動監査を走らせます。
  - integrity_check
  - 重複監査
  - stale apply監査
  - 秘密情報スキャン
- 違反が1件でも出たら即停止し、ラベルを取り消します。

## 5. 承認者の区分

| 項目 | 必要なもの |
|---|---|
| 完了定義の変更、新ラベル、72hの格下げ、P1シナリオ内容、P4宣言 | **ユーザーの明示承認** |
| 実provider接続、文脈組み立て、時間依存テスト、証跡の依存hashと影響範囲リセット規則、自動監査 | **実装とSWEレビュー** |
| 既存のsoak・S0証跡の再ラベル | **誰も行ってはならない** |

## 6. 最も強い反対意見とリスク

**実providerを今の段階で会話laneに入れると、検証済みの安全基盤（fence、冪等性、forget）を揺らします。**「まずmockでStable-0を固めてから接続する」という元の順序にも合理性はありました。

ただし、mock上の72hは実provider接続後にほぼ再取得が必要になります。そのため、二重コストを払うより、接続後に一度だけ観測する方が個人利用では合理的だと判断します。

残るリスクは二つです。
- **Pro利用枠の上限。** 個人利用では許容範囲ですが、エラー時の挙動は要テストです。
- **「完全に期待どおり」はLLMでは達成不能。** P1で有限のシナリオに固定しない限り、完了は永遠に来ません。
