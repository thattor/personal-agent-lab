## 2. D027 bare `answer:` semantics

**The current behavior is a regression against P002.** P002 requires an answer to be bound to the same work, question and epoch, and to resume only on a valid answer. The latest-Goal heuristic breaks that in two ways:
- It can pick the wrong Goal when several Goals exist.
- It fails silently when the latest Goal is not the one waiting.

Now that the explicit bound UI exists, the two answer paths also follow different rules. Keeping the legacy shortcut is not acceptable.

**Removing bare grammar entirely is also unsafe.** `answer: x` would then reach the Primary as ordinary conversation. That invites new unintended work, or a model guess at the target. It also drops the convenience the human accepted.

**Recommended behavior:** your proposed minimal change, with the conditions below.

1. **When a bare answer may route.** Route only when all of these hold:
   - there is exactly one CURRENT open, persisted, host-bound question row, where "current" means:
     - not superseded by a correction;
     - epoch current;
     - Goal not cancelled;
     - not invalidated by forget;
     - question cap not exhausted;
   - and there are zero legacy diagnostic waits anywhere.

   A legacy wait counts toward ambiguity but can never be a route target. This avoids attaching input to a phantom ID, and avoids hijacking a diagnostic the user may have meant.
2. **Freshness guard (the main remaining wrong-target risk).** Bare text carries no epoch. If a correction replaced Q1 with a new question Q2 on the same Goal, an answer written for Q1 would route to Q2 as the single match. So route only if:
   - that question's id and epoch were shown in the most recent host-delivered output;
   - and the set of open questions has not changed since that output.

   Otherwise give a clarification. After a restart, the bare path requires the question to be shown again; explicit bound answers still work immediately.
3. **One validation path.** The host resolves the binding atomically, capturing the epoch at that moment. It then calls the exact same handler as the explicit bound answer, with the same rejection rules for late, duplicate, cancelled, forgotten and restarted cases. A routed answer counts toward the two-ANSWERED cap. The cap is never reset.
4. **When it does not route.** With zero or multiple matches, or a failed freshness check:
   - show a visible notice listing the explicit answer forms, and the candidate questions when there are several;
   - make no control or state change, no persisted answer and no model or cost call;
   - do not reinterpret the input as an ordinary request.

   A duplicate bare answer after a question is answered hits zero matches, so it is harmless.
5. **Legacy diagnostic wait.** Its existing explicit or diagnostic semantics stay unchanged. One user-visible change remains: a bare answer no longer resumes a diagnostic wait. The notice should point to the diagnostic form.
6. **Out of scope.** No automatic question for an ineligible template (that case simply has zero matches). No new task type, retrieval, provider, multi-Expert or memory work.

**Tests to freeze before code:**
- 0, 1 and 2 open questions;
- 1 open question plus a legacy wait;
- the question set changed since the last output;
- an answer after a correction or a cancel;
- a duplicate answer;
- a restart while waiting;
- the cap exhausted;
- a forgotten source;
- an ineligible template;
- explicit bound answers still preferred and unaffected.

**Process:** this implements an adopted binding requirement rather than adding scope. It still changes accepted user-visible grammar, including dropping bare resume for diagnostic waits. So:
1. Record it as a D-027 input-semantics decision.
2. Have SWE-2 High review the contract.
3. Get the human's direct confirmation.
4. Only then change code.
