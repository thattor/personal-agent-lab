# Verdict

**Adopt a Primary-only correction, with two changes to your wording.** Native, Expert, validator, decoder, Store and host acknowledgement all stay unchanged. Candidate `4a5ec27` is **FAIL** on the frozen N22 oracle, and nothing here changes that.

**Is this new scope?** No. D021 already requires that both send-only and draft-and-send requests produce no Goal plus an explanation, and that the user may separately ask for a local-only draft. The correction makes the prompt conform to accepted behavior; it does not widen it. The existing text even says "use none for … unsupported requests." The defect is that the contract contradicts itself on compound requests.

# Root-cause challenge

Your inference holds, but it misses two contributors.

1. **"do not *silently* perform a partial compound request"** implies that announced partial work is allowed. This is the main defect. **Agree.**
2. **"Use none for … unsupported requests"** reads naturally as "requests that are entirely unsupported." A compound request contains a supported piece, so this sentence never fires. **Agree.**
3. **Missed: the model re-scoped the request on the user's behalf.** The N22 reply says 送信はご自身でお願いします ("please send it yourself") and the spec says 送信はしない ("will not send"). The model turned "draft and send" into "draft for you to send," which is a legitimate request in its own right. The fix must say outright that the model must not narrow the request itself.
4. **Missed: C038 plausibly added pressure.** "use local_draft now" is unconditional drafting pressure placed right next to the compound language. Old N22 was NOT_RUN, so you are right that this cannot be proven. Placing the gate *before* the drafting guidance removes the pressure either way.

**Host acknowledgement:** this is not a cause, but it is why partial work is unacceptable. The model's caveat is discarded, so the user saw only "draft acknowledged" with no mention of sending. That is exactly the papering-over that D021 prevents.

# Regressions your wording would introduce

**1. Over-blocking drafts the user will send themselves.** This is the main new risk. "Any unavailable external action" can easily catch requests like:
- "Draft an invite I'll send tomorrow"
- "Draft a message to send to Bob"
- 送る用の文面を作って ("make a text for sending")

These are ordinary local drafts. The prompt must separate "you, assistant, send it" from "a draft whose purpose is to be sent." Your quoted/hypothetical/negated carve-out does not cover this case.

**2. "Optionally offer a local-only alternative"** can produce a reply like "I'll prepare the draft…" while the action is none. The reply must not promise or start anything.

**3. Acceptance turn.** If the model offers a local-only draft and the user answers "yes" or お願い ("please do"), that is a separate, local-limited request under D021. Your text says "a separate user reply limiting work to local-only," which a model may read as requiring the user to restate "local only." State that accepting the offer qualifies. "Yes, and send it" goes back through the gate.

**4. Uniform blocking of other effects. Accept this deliberately.** The gate also blocks cases such as:
- "cancel that and email Bob"
- "remember X and send it"
- answering an Expert question plus sending
- "correct the draft and send it"

This is consistent with "none for the entire request." Explicit control buttons remain usable on their own. Keep the rule uniform; carve-outs re-create the ambiguity.

**5. Non-send unavailable actions.** Examples are scheduling, posting, and "look it up then draft." The existing "unsupported → none" text already covers these, so including them is not new scope. However, the frozen oracle tests only sending, so treat them as unverified beyond the independent items below.

# Exact recommended change (`primary_prompt` only)

**(a) Insert** after `Do not create work for hypothetical/reported/negated requests.` and before `For an actual local draft request, …`:

> `Before any drafting or other action decision, consider the whole current request. If it asks you to perform any unavailable action, such as sending, posting, scheduling, browsing or purchasing, even together with work you could do, use none for the entire request and do not narrow it yourself. Say you cannot do that part; do not start, promise or perform any part. You may offer a local-only draft that the user can request separately. A request for a draft that the user will send or use themselves is not an unavailable action, nor is a quoted, negated or hypothetical mention of sending. A later user reply limiting the work to local-only, including acceptance of your local-only offer, is a new request: evaluate it normally.`

**(b) Replace** `Explain unsupported work without claiming it happened; do not silently perform a partial compound request.` with:

Removing "silently" is required. If it stays, the old permission competes with the new gate.
