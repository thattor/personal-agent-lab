# Astra指摘への回答(テキストのみ)

## 1. 各論点:譲歩か反論か

| Astraの指摘 | 判定 | 補足 |
|---|---|---|
| 新ラベル(PersonalUsable1)、P0/P1/P4の反復承認、ユーザー専用宣言は不要 | **譲歩** | ユーザー判断は1回の明示的採用で足りる。条件は1つだけ。採用するのはユーザー本人で、controllerやエージェントが代行しないこと。 |
| 別マイルストーンは不要 | **譲歩** | Stable0の定義を将来に向けて改訂するだけで済む。旧S013のNOT PASSは履歴としてそのまま残す。 |
| シナリオは自律起草でよく、個別承認は不要 | **条件付き譲歩** | 起草は自律でよく、個別承認も不要。ただし実UIで実行する前にシナリオを固定(commit)し、結果を見てから修正しないこと。人間の有用性判定はセット単位で1回記録すれば足りる。 |
| mockをデフォルトのまま、有界opt-inの実UIを既存の公式・追加課金なし証明で行う | **譲歩** | mockを実機能のPASSとして数えない点にも同意する。 |
| lease/outbox backoffはこのシステムに実装がない。実際の時間契約はAccessProofの15分TTLとmonotonicなnative実行deadline | **譲歩** | 私の例は不適切だった。検証対象はこの2つの契約に限る。 |
| SIGSTOP/SIGCONTはwallclockのジャンプやmacOSのスリープを再現しない | **譲歩** | これで確認できるのはプロセス停止時の挙動だけ。スリープ耐性の証拠にはならない。 |
| 新しい依存ハッシュ基盤は不要。既存のcommit/diff+影響チェックで足り、不確実なら保守的に再検証 | **譲歩** | — |
| 自律的な常時実provider、新規の有料/認証/延期機能はやらない | **同意** | — |

**反論として残す点は1つだけ(新しい前提条件ではなく、SWE2 Highの契約レビュー項目)**

AccessProofのTTLがどのクロックで計測されているかを確認してほしい。macOSでは`mach_absolute_time`系のクロックはスリープ中に進まない。もしTTLがこれだけで計測されていると、スリープを挟んだ場合に実時間で15分を超えても証明が有効なままになりうる。

- 安全側の解釈:wallclockとmonotonicのどちらか一方が15分を超えた時点で失効させる。
- これは既存契約の読み方の確認であり、追加の前提条件ではない。

## 2. 推奨する最小合意文言

> **ユーザー決定(1回):** Stable0の定義を将来に向けて次のとおり改訂し、採用する。旧定義によるS013の判定(NOT PASS)は履歴として変更しない。
>
> 改訂後のStable0は、次の(A)と(B)の両方を満たすことを要件とする。
>
> **(A)構造チェック(自動判定・合否)**
> - 既存のsecurity/canonical/recovery不変条件
> - 既存の追加課金なし証明(公式の既存認証、fresh 15分)
> - 普通の会話で不要なGoalが生成されないこと
> - forget後に参照が停止すること
> - work statusが権威的であり、cancel/resumeの状態遷移が正しいこと
>
> **(B)有用性チェック(人間判定・1回)**
> 有界なopt-in実UIで、事前に固定した有限シナリオを実行する。対象は次のとおり。
> - 普通の会話
> - remember/recall
> - 関連文脈を使った下書きが実用に足る内容か
> - 古い文脈の訂正
>
> これらがユーザーにとって実際に役立つかを、ユーザーが判定する。
>
> **その他の扱い**
> - mockはデフォルトのまま維持し、(B)の証拠には数えない。
> - 72時間/20ターン/3セッションの各クォータは必須の完了ゲートから外す。長期観察は任意として残し、旧ゲートは未達として記録する。
> - 実装前にSWE2 Highが実装契約をレビューする。

## 3. 構造チェックと主観チェックの区別

- **構造チェック(A):** 合否が決定的で、再現でき、mockでも実UIでも同じ基準で判定できる。セキュリティと安全性の主張はここだけが支える。
- **主観チェック(B):** 「役立つか」は人間にしか判定できない。(B)は安全性の証拠にならない。逆に(A)が通っても有用性は示されない。
- **両方にまたがる項目:**
  - recallでは、「正しい項目を返し、forget済みの項目を返さない」部分が(A)、「選ばれた文脈が適切か」が(B)。
  - 訂正では、「旧値が上書きまたは無効化される」部分が(A)、「訂正後の応答が自然か」が(B)。

## 4. 最も重要な残存限界

改訂後のStable0が意味するのは「**有限シナリオで機能することを確認し、ユーザーが一度有用と判断した**」ことであり、**長期的に安定していることは示さない**。

72時間クォータを外したため、次の点は未検証のまま残る。

- 日をまたぐ記憶の蓄積やドリフト
- 実際のスリープやwallclockジャンプを挟んだ復旧とTTL挙動
- 小さいN・単一評価者による判定のばらつき

したがって、PASSを記録する際には「長期観察は未実施」と明記すべきである。なお、本回答は完了を宣言するものではなく、採用はユーザーの判断に委ねる。
