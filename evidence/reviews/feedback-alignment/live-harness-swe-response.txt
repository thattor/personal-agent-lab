# Branch A — live-provider harness

## A.1 Holes in the supplied source that the contract must close

**H1 — `Runtime.close()` kills a shared provider.** `close()` calls `executor.stop()` (which calls `provider.stop()`) and then `provider.stop()` again. `NativeClaude.stop()` sets `_stopped=True` permanently; every later `complete()` raises `'stopped'`. A shared provider across per-case hosts cannot survive the first host teardown. The harness must interpose a pass-through facade whose `stop()` is a no-op, hold the real `NativeClaude` reference itself, and call the real `stop()` exactly once at global teardown. The facade is also the right place for invocation accounting (A.2).

**H2 — `build_provider` defaults `native_call_limit` to 16, not 20, and `consume()` is one-shot.** `AccessProof.consume` uses `O_EXCL` on a content-hash marker — a second host process loading the same proof gets `proof_consumed`. Therefore the six disposable hosts cannot be separate `server.py` processes; the matrix requires one harness process that: loads the proof once, consumes the marker once into an explicit per-run marker dir (the default `runtime/native-proof-use` is cwd-relative — do not rely on it), constructs `NativeClaude(proof, max_calls=20)` explicitly, and then runs six `Runtime` + `make_server` pairs sequentially on six distinct DB paths and ephemeral ports (`port=0`). Consequence: all six hosts share the harness PID. Evidence must record `started_at`, DB path, and port as host start identity, with the shared-PID fact stated rather than hidden.

**H3 — Cost accounting is invocation-count-only, and the count includes failures.** `NativeClaude.complete` decrements `_remaining` before the auth subprocess and generation run. A failed call still consumes budget (conservative — good) but the evidence must split "attempted / auth-failed / generation-returned / decode-rejected". Each generation actually spawns two CLI invocations (`claude auth status` + `claude -p`); the auth call is not a generation but must be logged. There is no token telemetry in `--output-format text` mode: "cost proof" can only ever be (a) the no-extra-charge attestation, (b) generation count, (c) subprocess records. State this limitation in the contract; do not claim per-token cost evidence. The facade should log, per call: sequence number, prompt kind (`DRAFT` vs `CONVERSATION`), prompt hash, a sanitized prompt copy (needed for F1 absence checks), response hash or error phase (`_last_error` is only `auth_unavailable`/`generation_unavailable`), duration, and PID set from `provider._calls`.

**H4 — Host-internal requeue can silently burn a second real generation inside the poll window.** `store.fail` with `check_status='fail'` (the `EvidenceRejected` path — e.g., malformed JSON, bad citations) requeues the same goal once, and `unverified` requeues too. The worker claims the requeue immediately; the harness only learns of the outcome on its next poll. That is a host-designed bounded retry, not a harness blind retry — but it issues a second identical real call with no new information. For a live run the smallest deterministic fix is a gate in the facade: `complete()` acquires a per-case permit; the harness issues exactly the case's planned permits (K1:1, A1:2, G1:1, T1:1, P1:3, F1:1 = 9 total) and closes the gate the moment an unexpected outcome or the deadline arrives. A gated-off call raises a distinct harness error without decrementing `NativeClaude._remaining` and without spawning `claude`. This also makes "cap even on host crash" deterministic: a crashed/requeued attempt can never reach the provider unplanned.

**H5 — 900 s wall vs per-call worst case.** Each `complete()` can take ~138 s (10 s auth + 120 s generation + grace). Nine planned generations could exceed 900 s if calls approach timeouts. Two mitigations already exist and two are needed: (a) the proof itself expires at `verified_at + 900` and `proof.check()` runs inside `complete()` — post-expiry calls fail `proof_expired` without spending; mint the proof immediately before the first host starts so the proof window is the wall clock; (b) a harness watchdog thread holds `deadline = monotonic() + 900`, and on expiry calls the real `provider.stop()` (writes `x` to all control pipes → supervisors kill `claude`), then closes runtimes; (c) before each case, check remaining wall against the case's worst-case bound and stop the run cleanly as "wall insufficient" rather than entering a case that cannot finish; (d) `Runtime.close` blocks in `_conversation.shutdown(wait=True)` — bounded because `provider.stop()` precedes it, but teardown code must tolerate `close()` raising (worker-alive path leaves the flock held — harmless since DB paths are per-case disposable, but don't reuse a path).

**H6 — Crash/orphan guarantee is unverifiable from the supplied source.** `native_supervisor.py` is not in the snapshot. The design implies the control pipe death (or `x` byte) kills the child `claude`, but this must be proven by a contract test: start a generation, `SIGKILL` the harness process, assert no `claude`/`native_supervisor` processes survive after a grace period. If the supervisor does not kill on pipe EOF, an orphaned `claude` is both an unaccounted generation and a leaked process — blocking hole until tested. Also note the `finally` in `supervised_text` calls `communicate(timeout=6)` which can raise `TimeoutExpired` and mask the original `ProviderUnavailable` — minor bug, record it.

**H7 — The bare `answer:` shortcut must not be used by the harness.** `submit()`'s `lower.startswith('answer:')` path resolves `_latest_goal()` outside any transaction (TOCTOU) and — worse — the answer record stored is the raw ingress message *including* the `answer:` prefix, while `control['text']` is only checked truthy. All six-case answers must go through explicit `control={'action':'input','question_id':…,'epoch':…,'text':…}` with `goal_id` set, read from `/api/state` (the `questions` table is in `inspect()`), and `text == control['text']` (see H8).

**H8 — Answer content channel is under-validated.** In `_control` `input`, the persisted answer source is `source_record_id` = the ingress message record, i.e., the message `text`, while the gate only requires `control['text']` truthy. A message with `text='ok'` and `control['text']='<the real answer>'` stores "ok" as the answer the model sees. The host does not cross-check them. Contract options, smallest first: (a) harness contract — always send identical `text` and `control['text']`, and a contract test asserts the stored answer record equals the intended string; (b) host assert equality for `input` controls — a one-line host change, but that is a code change needing the same freeze discipline. Recommend (a) now, (b) as a flagged candidate correction.

**H9 — Seeding via `Store.record` is load-bearing and untested here.** The given records for K1/F1 must enter attempts' source manifests via `store.context()` — the excerpted code doesn't show `context()` or `record()`'s signature/defaults. Before the live run, a contract test must prove: `Store.record(key,'user',text,…)` produces a `usable=1` record, appears in `context()['manifest']`, and therefore in `attempt['sources']` and the actual `DRAFT` prompt captured at the facade. Seeding through `submit()` instead would cost a `CONVERSATION` generation per seed and pollute the count — the matrix's "Store.record only" is also a cost requirement.

**H10 — Epoch-capture race on answers is avoidable deterministically.** `input` requires `goal.question_id == question_id and goal.epoch == epoch`. Any drift → `InvalidTransition` → 400. The harness must serialize: submit → wait `runtime.idle` → read `/api/state` → send bound answer → wait idle. Never fire-and-forget; a rejected answer is not retryable under "no blind retry" unless the rejection is provably a stale-read race, so prevent the race by sequencing rather than handling it.

**H11 — HTTP/UI mechanical contract.** `allowed()` requires `Host` exactly `127.0.0.1:<port>` and `Origin` `http://127.0.0.1:<port>` on POST — `localhost` gets 403. The browser tool must navigate to the literal printed URL. POST to anything but `/api/message` → 405 (this is the read-only-inspect evidence). ACK for a lost response is `GET /api/operation/<key>` — use it, never resend. Responses are stored under `response:<key>` via dedupe; the response Future is stripped from the ACK.

**H12 — Provider environment fragility.** `native_environment()` strips all proxy variables and tokens; `claude auth status` may fail in proxied environments → `auth_unavailable` → real failure at case 1. Also `--safe-mode`/`--strict-mcp-config`/`--disable-slash-commands` compatibility depends on the installed CLI. Preflight (before consuming the proof): `claude auth status` must return `loggedIn && authMethod=='claude.ai' && subscriptionType in (pro,max)`; record CLI version. Preflight does not consume the marker or budget.

**H13 — Diagnostic mislabels (minor).** In `complete()`, `proof.check()` after auth still reports `last_error='auth_unavailable'` if it raises; evidence readers should not over-trust the phase label. `status()` recomputes expiry live — fine for UI.

**H14 — Model-behavior expectations are not host invariants.** K1 "no question", G1 "no invented concrete date/place/name", A1 "one grouped question", T1 "eligible incomplete_preview" (the model could return `kind:'complete'` containing literal `{{date}}` and the host would legitimately complete it — nothing in `complete()` rejects placeholder text), P1's conditional exhaustion, F1 "asks essential unknowns" — all are deviations the runner must *detect and stop on*, not assert. The runner contract must define "REAL failure" explicitly. Recommended: stop on (a) any infra/provider/proof/contract error outcome, (b) any outcome whose kind differs from the case's expected terminal shape, (c) deadline. `unverified` is a legal terminal only for T1 (`incomplete_template`) and P1 (`clarification_exhausted`); any other `unverified` stops the run. No resampling, ever.

**H15 — UTF-8/JSON boundary inventory (verified safe + one open).** `decode_draft` correctly rejects: duplicate keys, nonfinite numbers, non-dict/wrong field sets, BOM, NUL, lone surrogates (strict `utf-8` encode), oversized payloads; `validate_placeholders` rejects stray `{{`/`}}`. `write_draft` re-checks byte bound post-`sanitize` and hashes actual stored bytes; `complete()` does full readback (decode, hash, size, NUL/BOM). Open hole: `ProviderExecutor` builds prompts with `json.dumps(…, ensure_ascii=False)` — a stored record containing an unpaired surrogate (reachable via JSON `\ud800` escapes in a seeded or UI message) produces a prompt that fails `encode('utf-8','strict')` in `supervised_text` → `ProviderUnavailable` → real failure. Whether `sanitize()` normalizes surrogates is not visible in the snapshot; contract-test it. Strict-JSON means any model preamble/fencing → `EnvelopeRejected` → `EvidenceRejected` → `fail` → host requeue → gated off (H4) → run stops. Correct and intended, but it means "model produced fenced JSON" is a run-ending outcome — accept that in the contract.

**H16 — `Control`/`questions` mismatch class (diagnostic waits).** `_wait()` sets `goal.question_id` with **no** `questions` row. In the live run this only matters for evidence reading: `waiting_input` with reasons like `repeated_failure_requires_diagnosis`/`reference_stopped`/`retry_budget_exhausted` must not be counted as "open question" for A1/P1 expectations — count `questions` rows with `status='open'`, not `goal.question_id`. (This same asymmetry is central to Branch B.)

**H17 — "Avoid starting revised host/provider proof per case silently."** Pin at freeze: hash every `pal/*.py` + the matrix JSON + fixture strings into the evidence manifest; re-hash before each case start and at teardown (readback); any drift aborts. The provider and marker are created once; the contract must state plainly that a second `NativeClaude`, a second `consume`, or a `MockProvider` fallback aborts the run rather than proceeding.

## A.2 Smallest safe harness design

1. One stdlib-only Python process. Phases: pin hashes → preflight CLI auth (no proof) → write operator proof file → `AccessProof.load` → `consume` into per-run marker dir → construct `NativeClaude(max_calls=20)` → wrap in gated accounting facade.
2. Facade: delegates `identity/status/proof`; `complete()` = `acquire_permit → NativeClaude.complete → log`; `stop()` = no-op; `register/unregister` used to snapshot child PIDs.
3. Six iterations: new temp DB path → `Runtime(provider=facade)` → `make_server(runtime, port=0)` → seed via `Store.record` (K1, F1) → optional supported-API forget (F1, explicit `source_id` control, not `forget that`) → POST request → wait idle → drive UI via installed browser tool at the literal `127.0.0.1:port` URL → bound answers where the case requires → capture `/api/state`, `/api/artifact[_status]`, `/api/operation`, `inspect()` → close runtime → next case.
4. Watchdog: deadline thread + per-case budget check + failure monitor polling `inspect()` for outcomes/events; on any trigger: gate closed → real `provider.stop()` → close all runtimes (tolerating raises) → fsync evidence.
5. Evidence: append-only JSONL fsync'd per event (survives harness crash); per-call records from the facade; per-case host identity; final artifact bytes + hash vs receipt readback; source/fixture re-hash; explicit "synthetic answers are not human attestation" labels; UI observations recorded as "rendered DOM/browser capture", never "user saw".
6. Cases generated by loading the frozen matrix file — never a hand-copied list; a contract test asserts runner case IDs == matrix IDs (covers "controller audit coverage of tests versus actual cases").

## A.3 Contract tests to freeze before substantial harness code

1. Envelope fuzz table (dup keys, `NaN`, BOM, NUL, lone-surrogate escapes, oversize, placeholder mismatch, banner spoof) → expected rejection reasons.
2. Scripted-stub-executor runs of all six case shapes at the `Store`/`Runtime` level: T1 preview artifact bytes + `role='preview'` + no PASS; P1 exhaustion preview is host-authored and quotes the last question; F1 manifest/prompt exclusion + `usable=0` retained in `inspect()`.
3. Answer binding: correct/wrong epoch, correct/wrong `question_id`, duplicate-key replay, `text ≠ control['text']` documented behavior, diagnostic `question_id` (no `questions` row) → `InvalidTransition`.
4. Proof: malformed schema, duplicate key, nonfinite, >4096 bytes, expired, `consume` twice → `proof_consumed`.
5. Cap: `max_calls=1` → second call raises without spawning (assert via `_calls`/process table).
6. Gate: denied call never reaches `NativeClaude` (count and process table unchanged).
7. Orphan/kill: `SIGKILL` mid-generation → no surviving `claude`/supervisor; `SIGTERM` → ordered teardown evidence.
8. HTTP: `localhost` Host rejected, POST `/inspect` 405, `operation()` absent/accepted paths, `artifact_status` stale flag after forget.
9. Seed→context→manifest→prompt inclusion (stub executor captures `order.sources`), and post-forget exclusion.
10. Shared-provider lifecycle: facade survives `Runtime.close()`; second host functions; real `stop()` once.
11. `sanitize()` surrogate/emoji/ZWJ output is strict-UTF-8-encodable (closes H15's open item).
12. Evidence schema self-check: every matrix `evidence_requirements` item has a producer in the runner.

# Branch B — bare `answer:` semantics

## B.1 Verdict on the proposal shape

Opus's diagnosis is correct on both ends: latest-Goal routing is a wrong-target regression against the adopted binding requirement, and letting `answer: x` fall through to ordinary conversation is worse (new Goal, model call, cost). The fork is between Opus's *conditional route* and the *notice-only* alternative. My recommendation: **notice-only is the smallest safe contract**, and the conditional route is acceptable only with the cheaper freshness mechanism below — which also requires conceding that "shown" can never mean "human saw".

## B.2 Can the host establish shown-freshness honestly?

No — and the contract must say "emitted", never "displayed" or "seen". Two candidate anchors:

- **`/api/state` responses degenerate.** The UI polls state continuously; "the last response contained this question" is true at essentially all times and proves nothing about what was on screen when the user typed. Do not build freshness on API reads.
- **The canonical event log does not degenerate.** `deliver()` already turns state transitions into durable assistant records from `events`. The meaningful invariant is: *the most recent state-changing event for this Goal is the `goal.waiting_input` event whose payload carries this `question_id` and current `epoch`.* Any correction, cancel, forget-invalidation, epoch bump, or new question emits a later event and fails the check. This is Opus's "most-recent host-delivered output + unchanged set" expressed in state the host actually owns — the "unchanged set" clause folds in, because every set change is itself an event.

Restart ("question must be shown again") cannot come from durable state — durable events survive restart and would wrongly satisfy freshness. The honest minimal mechanism is an **in-memory "delivered this process" flag** set when `deliver()` emits the `waiting_input` event during the current process lifetime. After restart, pre-existing waits have no fresh emission, so bare answers get the notice while explicit bound answers still work — exactly the required asymmetry. A *durable* delivery-set token is therefore overengineering twice over: it adds a schema for a guarantee events already give, and durability is the opposite of the restart semantics you want.

Residual risk to name honestly: a correction replacing Q1 with Q2 emits the Q2 `waiting_input` event; a user typing an answer meant for Q1 then still binds to Q2. The freshness check cannot fix that — it only narrows the window to "host's canonical story has not changed since emission". That residual is the price of keeping bare routing at all, and it is the strongest argument for notice-only.

## B.3 Atomicity

Whichever variant is chosen, resolution must happen **inside** the control transaction, not in `submit()`'s read-then-send pattern (the current `answer:` path races exactly this way). Contract: a distinct internal action (e.g. `action:'unbound_answer'`) whose `_control` branch re-checks, under the same txn, all of: exactly one `questions` row `status='open'`; its goal `waiting_input` with `question_id`/`epoch`/`revision`/manifest all current; zero diagnostic waits anywhere (goal `waiting_input` with `question_id` lacking a `questions` row — these count toward ambiguity but can never be targets); event-recency and same-process-delivery flag; then delegates to the identical `input` handler so late/duplicate/cancelled/forgotten rejection and the never-reset `answered` cap apply unchanged. Any failed condition → visible notice, no mutation, no model call, no reinterpretation as request.

## B.4 Notice-only (recommended smallest design)

`answer:` is recognized as grammar but never binds. Response: a canned, stored assistant notice listing the explicit answer form and, when ambiguity exists, the candidate open questions; the raw text is recorded as a user record (raw history) but creates no Goal, no question, no control, no provider call. Diagnostic waits keep their existing explicit/diagnostic semantics — the notice points to the diagnostic form. Ineligible-template input has zero open questions → same notice path. This deletes the entire wrong-target class, needs no freshness machinery at all, and costs only the convenience — which the explicit UI forms already provide and which P002's evidence model doesn't use anyway.

## B.5 What needs Opus/human vs what is implementation contract

Needs the D-027 semantics decision and human confirmation (user-visible grammar changes): bare-answer routing vs notice-only; dropping bare resume for diagnostic waits; notice wording; and — if routing is kept — whether the event-recency + same-process-delivery mechanism satisfies Opus's "shown" intent, since it demonstrably cannot mean human perception. Implementation-only (no Opus needed): in-memory delivery flag, notice as a stored canned record, resolving inside `_control`, harness gating.

Frozen tests before any code: Opus's list plus "bare answer while only a diagnostic wait exists", "question emitted pre-restart only" (→ notice), and "`answer:` text must not create a Goal or provider call". Keep the existing shortcut untouched until the decision is recorded and the human confirms — the current path is unsafe but changing it now would preempt the review itself.
