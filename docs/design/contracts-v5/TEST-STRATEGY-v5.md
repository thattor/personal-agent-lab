# PAL v5 テスト方式と具体例

2026-10-09。対象: PAL-contracts-v5.md / CONTRACT-AUDIT-v5.md。
本人依頼に基づき検証計画に採用する方式を具体化した設計成果物。製品・テストコードの実装、実行試験、正本への反映は未実施。既存CT/E2Eを置き換えず、検証方法を補足する。

## 1. 採用する方式

| 方式 | PALへの適用 | 役割・限界 |
|---|---|---|
| 利用側・提供側の契約テスト | C01–C15の共有例を両側で使う。利用側が正しい要求を作り、返答を使えることと、提供側が必要な返答を返すことを別々に検証 | 型だけでなく値の対応・エラーを確認。保存や競合の正しさは別の機能試験 |
| 表形式の単体・状態遷移テスト | v5状態表の前状態→操作→後状態と、変えてはいけない項目を確認 | 停止・再開・変更・質問回答を重点化。全状態の全組合せを自動生成する基盤は作らない |
| 制御した順序による故障・競合テスト | 保存後・応答前など決めた境界で中断。pause/completeの両順序を再現 | sleepによる偶然の競合を避ける。異常注入は一時DBとfake外部接続で行う |
| 早期の小さな全体結合 | INT-03から依頼→実行→保存→表示を通す。INT-08で9シナリオを統合 | fake全体成功と実モデル・実接続成功を分けて記録 |

単体を手早く回し、接続を十分確かめ、重い全体試験を主要経路に絞る。テストピラミッドは費用配分の参考であり、件数比率や網羅率のノルマではない。

## 2. 最小限の実装方法（開発チャット向け）

- unittest / subTestで表形式のケースを実行。tempfileとsqlite3で一時DBを分離。unittest.mockは外部境界に限定する。
- 共有契約例はC番号、CT番号、契約版、前提、入力、必要な出力、拒否入力を持つ。時刻や生成IDの完全一致ではなく型・対応関係を確認する。
- 利用側は実際の要求生成と応答処理を動かす。提供側は同じ例を公開入口へ渡す。両側で別々に都合のよいfixtureを作らない。
- fakeにも公開契約の同じ例を適用し、その後に実モジュール同士を接続する。fake成功だけでは実装完了にしない。
- 保存結果・状態は公開読取り口から確認し、必要な永続化試験では一時DBを再オープンする。メソッドの呼出し順だけを正解にしない。
- raceは同期点を明示して実行順を決める。復旧ではプロセス終了で初めて分かるケースのみ、一時DBの子プロセス試験を追加する。
- Pact/Broker、新しいテストDSL、分散基盤、全状態探索、網羅率目標は初期導入しない。共有仕様と同一リリースのモジュラーモノリスなので、契約例と標準ライブラリで始められるという設計判断。
- 専用の非自明な故障注入基盤が必要になった時だけ、既存の実装レビュー手順で検討する。

## 3. 契約例の試行（机上照合、実行PASSではない）

### CT-24: 仕事を作る接続 C03 → C02

前提: 未作成のkey K、許可範囲内の対象、存在する原記録、IDなしの条件を1つ持つDraftBrief。
操作: PRIがcreateを呼び、返ったgoal_idでget_workを呼ぶ。
確認:
1. 応答はqueued、WorkRefとexpert_idとgrantを返す。
2. 保存BriefにはTSK発行の条件IDがあり、目的・対象・制約・原記録への対応が保たれる。
3. 同じK/同じ入力の再送は同じ仕事を返す。Kを同じにして入力を変えるとconflict。
4. conditions=[]はinvalid_input。仕事作成も外部操作も発生しない。
方式: 利用側/提供側の契約テスト＋保存・再送の機能試験＋実接続。
机上結果: v5共通型/C03/C02から期待値を導ける。実装後は生成IDの文字列を固定せず、保存後の一致を検証する。

### CT-07: 質問中に停止し、回答してから再開 C04/C10/C13

| 手順 | 期待状態・確認 |
|---|---|
| runningからask | waiting_input、質問ID Qを保存 |
| pause | paused、Qは残る |
| Qへのanswer | paused、回答を保存しQを解消。仕事は動かない |
| 同じ回答keyを再送 | 同じ結果。回答・通知の効果を重ねない |
| resume | queued、同じgoal_idを維持 |
| claim | running、保存済み回答を参照できる |

方式: 表形式の状態遷移＋TSK/RUN接続。外部接続spyでpaused中の新規呼出し0件を確認。
机上結果: 各段階の前後状態はv5から決められる。会話の言い回しは採点しない。

### CT-08: 停止と完了の競合 C10

前提: 現行WorkRef、利用可能な現行成果物、全必須条件metの保存検証がある。
A: pause確定→complete。完了を拒否し停止意図を維持。進行中呼出しを回収してpaused。
B: complete確定→pause。completedを維持し既に完了であることを返す。
方式: 同期点で順序を固定した2ケース。単なるランダム同時実行を成功根拠にしない。
机上結果: 業務上の結果は規定済み。ただし「既に完了」と停止要求中の拒否をResultのどのcode/valueで返すかはv5に完全には固定されていない。実装開始時の共有契約例で両側を揃える。本人判断を要する事項ではない。

### CT-04: 外部取得を保存した直後に中断 C07/C13

前提: fake外部取得が1回成功し、EXE台帳にsucceeded/取得本文が保存済み。
操作: RUNへの返答前に終了→一時DBで再起動→get_by_keyで照会。
確認: 外部取得回数は1回のまま。保存済み結果を回収し、現行revision/出典可用性を確認して処理を続ける。不明な実行を成功と偽らない。
方式: 永続化・復旧の接続試験。台帳保存前に落ちたunknownは別ケースとして扱う。
机上結果: v5に回収経路あり。fakeでの復旧成功とGitHub実接続の成功は別の証拠が必要。

## 4. 机上試行で明確になったこと

「文書に接続の記載がある」と「そのまま実行できる契約例が全て揃う」は異なる。上記CT-08のようなエラー表現の詰めは残る。前回の『既知の未処置の接続欠落なし』は文書上の主要経路に限る。実装前のINT-01で以下を揃える。

- 共通Resultに沿って、状態別の拒否codeと返却valueを表にする。推奨は同じ版の状態不適合=conflict、版不一致=stale、未知ID=not_found。既に完了もconflictと説明を返し、C02で現状態を読めるようにする。これはv5への提案であり、共有契約例の確定時に本文と両側を同時更新する。
- 停止後の新規呼出し禁止など、出力型だけでは表せない期待動作を機能テストに分離する。
- 契約の期待値を変えて失敗を隠さない。不一致は契約の曖昧さか実装違反かを切り分ける。

これは製品の追加機能や設計の全面変更を求めるものではない。契約例を具体化する工程で解消する局所的な技術事項。

## 5. 実装へ渡す順序と証拠

1. INT-01: C01–C15の型、共有例、拒否表を揃える。CT-24/07/08/04を最初の代表ケースにする。
2. 各担当: 自分の提供側と利用側の契約例、重要な単体テストを通す。新規の例を必要以上に増やさず既存CTへ紐付ける。
3. INT-02/03: 実接続の小経路と、実モジュールを組み合わせた最短の全体経路を確認する。
4. INT-04以降: 記憶・質問・制御・復旧を追加するごとに関係するCTを確認する。
5. INT-08: 既存E2E-01–09を統合。実モデル/実接続/UIの証拠を取り、最終的な実用価値の評価へ進む。

結果は契約版、対象実装SHAと未コミット差分、ケースID、実行環境、fake/real、期待・実測、PASS/FAIL/NOT_RUN、証拠を残す。mockを実接続と呼ばない。失敗した接続に依存する統合だけを待ち、無関係なモジュールは並列で進める。
会話文の一致・文体の採点・固定時間の試用・入力回数のノルマは追加しない。

## 6. 参考資料と採用範囲

- Pact公式 How Pact works: https://docs.pact.io/getting_started/how_pact_works
  利用側の要求/期待応答と提供側の照合という考え方を採用。Pact製品は導入しない。Pactのメッセージ契約試験を、PALの保存・競合・業務動作試験と混同しない。
- Ham Vocke, The Practical Test Pyramid: https://www.martinfowler.com/articles/practical-test-pyramid.html
  速い局所試験と少数の主要全体経路を組み合わせ、test doubleと実提供者の乖離を確認する考え方を採用。固定件数比は採用しない。
- Python unittest公式: https://docs.python.org/3/library/unittest.html#distinguishing-test-iterations-using-subtests
  subTestによる表形式のケース実行を採用予定。現在テストコードは作っていない。
