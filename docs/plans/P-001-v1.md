# P-001 v1 — Personal Agent Lab 全体開発計画案

Status: PROPOSED / AWAITING_HUMAN_ADOPTION. Date: 2026-10-07.
Governance G-001 is active by direct human instruction; this product plan is not adopted. Stable-1 continues independently under D-021. This document is frozen when proposed; any substantive revision gets a new version. Adoption/status/evidence are recorded in DECISIONS.md, not by rewriting this version.

## Project：全体ゴール

会話の文脈を保持し、自然な依頼を受け、本人にしか決められないこと・不可欠な不足情報だけを確認し、許可された範囲で可逆な準備を進め、検証済みの結果・ブロッカー・必要な判断を返す個人用PALを完成させる。ユーザーに内部タスクの管理を押し付けない。

この計画案の最初の全体完成点はPAL-1.0。ローカルmacOS・private・本人が開始した利用の中で上記の価値を成立させる。システム発の定時起動・自発提案・通知は次の拡張案であり、PAL-1.0に暗黙に含めない。人間が別の最終範囲を選ぶ場合は変更案をOpusと議論して再提出する。

Projectの完了条件：
- G-P01：承認した各必須マイルストーンの完成条件が、対象版と証拠付きでPASS。
- G-P02：会話→記憶・呼び戻し→自然な依頼→必要な確認→ローカル準備→検証結果の返却を、事前に固定した代表的な利用シナリオと本人評価基準で実証。各機能の単独PASSだけでは全体完成にしない。
- G-P03：訂正・中止・忘れる／参照停止・重複防止・復旧・失敗表示・権限／費用境界が統合時も有効。未解決blockerの監査が完了。
- G-P04：本人の実際の総合有用性評価、最終フルテスト、版・利用方法・制約・残課題の記録、全体ゴールIssue監査とクローズ。
「自然」「関連」「必要な質問」は固定シナリオと評価基準に限った主張。あらゆる依頼の正しさ、常時運用、長期安定性を保証しない。子Issueのクローズ数は完成証拠にならない。

PublicSearch、iPhone/private accessの改善、外部通知は、本人用途に必要と分かった時に独立した権限・費用・完成条件付き提案にする。外部送信・購入・公開は本計画の自動実行範囲外。Dreaming、vector DB、multi-Expert、local inference、automatic procedure updates、arbitrary shell/repo/browser toolsは技術選択／拡張候補であり、入れること自体を完成条件にしない。既存の将来候補を削除したことにもならない。

## Issue：ゴールを持つ開発ループ

各Issueに親Project／milestone、ゴール、承認計画版、対象内外、Acceptance ID、依存関係、作業単位、証拠、結果評価、次の操作を記す。

ループ：正本／現状確認 → 未達条件に結び付いた作業単位を選ぶ → 必要なreview → test → 最小実装 → 検証 → 証拠・commit/push → 単位ゴール達成とmilestone／全体への寄与を評価 → 次の未達条件。

Issueの条件が全て証拠付きPASSなら、Issue自身のゴールを評価して閉じる。milestoneは各Issueの結果を束ね、ユーザーに約束した結果を別途評価する。Projectはmilestoneの結果を束ね、統合利用価値を別途評価する。下位の状態だけで上位を自動完了にしない。

## チェックポイントと計画変更

| 契機 | 評価・記録 | 次の動作 |
|---|---|---|
| coherent green作業単位 | 対象Issue／commit、目的、検証と証拠、結果、異常、全体への寄与、次の作業 | 達成なら次単位、未達なら原因診断・修正 |
| Issue完了 | AcceptanceとIssueゴール、milestoneへの寄与、依存解除、計画の前提が保たれるか | 閉じて次Issue。部分達成は閉じない |
| milestone終了／次段開始 | 全体への寄与、本人価値、前提・依存・コスト／権限、次段scope／固定rubric | 必須gate PASS後のみ完了。未承認段階へは進まない |
| 本人feedback、実不具合、同じ原因の反復、前提崩れ | 根拠、原因／未確定、影響範囲、修正または計画変更の必要 | 該当作業を止めて診断。独立した承認範囲は続行 |

materialな計画／scope／完成条件／優先順位／最終範囲の変更は、Opusと議論・合意 → IDと版を持つ具体的提案 → 本人判断 → 正本とGitHub更新 → 依存開発再開。合意できない変更は発効させず、異論と安全な代替を記録する。本人はG-001の運用ルール自体を明示的に変更でき、モデルが案件所有者に拒否権を持つという意味ではない。承認済み範囲内の通常の実装選択・不具合修正は計画変更と区別し、毎回人間承認を求めない。

変更提案には、判断ID、旧／新plan版、対象版・証拠、理由・差分、Opus結論と残る異論、推奨／代替、待つ作業／独立作業、解除条件を付ける。前の計画と失敗証拠を残す。本人回答は提示版に限って適用し、AIの説明・権限承認・別版への回答を採用と誤認しない。本人はhashを手入力する必要はなく、開発側が回答と提示版hashを照合する。

## 実行と管理の境界

mock default、fresh official no-extra-charge proof、D-020の期限／予算、host-only canonical writes、fixed criteria、security／cancel／forget／recoveryを維持。context量・provider呼出数・評価probe集合の数値上限は各段階の実行前に固定し、実行後に緩めない。SWE-2 Highはsubstantial実装前、Opusはdesign変更前。新auth・権限・費用・公開は別判断。停止済みの定期実行は再開しない。

PROPOSED milestone/Issueはゴールと候補を示す管理用登録であり実装許可ではない。ACTIVEの承認範囲だけを開発ループへ渡す。GitHub Projectsボードが使えなくても、全体ゴールIssue→milestone→Issueの追跡は継続する。
