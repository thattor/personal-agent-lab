# P-003 v1 — explicit answer forms, bare-answer notice

Status: PROPOSED, not human-adopted; HR-INPUT-001. Current shortcut is unchanged.

## Problem and recommendation

Bare `answer: ...` currently chooses the latest Goal. With multiple questions,
or a new question replacing an old one, this can resume the wrong work. Neither
API polling nor a host-emitted message proves which question the person saw.
Official Opus and standalone SWE-2 High agree on the smaller notice-only repair.

Recommend recognizing the existing leading `answer:` grammar but recording only
the sanitized user message and a static assistant notice in one transaction.
No Goal/question/control/event is created or changed, no answered count changes,
and no provider call occurs. Mid-sentence `answer:` stays ordinary conversation.
The notice lists no questions or source content, avoiding stale/forgotten leaks.

## Exact proposed notice

この入力は回答として送信されていません。新しい依頼としても扱われていません。質問に回答するには、その質問の回答フォームを使ってください。診断待ちの場合は、対象を指定する既存の入力APIを使ってください。

This was not submitted as an answer, and was not treated as a new request. To answer a question, use its answer form. For a diagnostic wait, use the existing explicitly targeted input API.

## What changes and what continues

- Normal question-card answer forms keep their explicit Goal/question/epoch
  binding and resume the same work. No new question count or budget is added.
- Bare `answer:` no longer resumes a diagnostic wait. The existing explicit
  diagnostic input API continues; no new diagnostic UI is implied.
- Existing API input is `POST /api/message` with a dedupe key, identical `text`
  and `control.text`, explicit `goal_id` and `control` containing `action: input`,
  `question_id` and `epoch`. This is an implementation contract, not a new
  conversational grammar or permission.
- Old messages, outputs and receipts stay historical; no DB repair is performed.

## Decision and release conditions

HR-INPUT-001 needs direct human confirmation of notice-only behavior, removal of
bare diagnostic resume and this exact wording. This is distinct from adopting
P-001 v2, project authorization, or the N1-07 usefulness verdict.

Alternative: retain the known unsafe shortcut pending a revised agreed design;
do not claim ambiguous bare answers are safe or release that acceptance item.
Conditional automatic routing is not recommended: even event freshness cannot
prevent text intended for Q1 from binding to freshly emitted Q2.

After adoption, record the exact source/version/hash and implement frozen tests:
zero/one/two questions, diagnostic-only, restart, running, cancel/forget,
duplicate receipt, no provider call/Goal mutation, mid-sentence conversation,
explicit and diagnostic API regression locks, raw-record reference-stop.
Until then, question-card forms and the independent bounded verification
harness proceed; new-flow human evaluation should avoid bare `answer:`.
